## 1. 背景与目标

用户希望做一个「局域网内可打开的网页版 AI 狼人杀」：支持人类玩家与 AI 玩家混玩、AI 填补人数不足、多个不同大模型扮演不同 AI 玩家、局域网内朋友通过浏览器加入。说明书由 Hermes 调研生成，本计划是审查结果 + 用户确认后的最终执行依据。

**执行人拿到本计划后，按「里程碑 M0→M6」顺序执行即可，每阶段自带验收标准。**

### 2.1 用户修正项（必须遵守）

1. **不做单轮 token 预算限制**：说明书第 3 节「单局 token < 5 万」、第 13.2 节「token 成本爆炸」条目全部移除，不做任何 token 计量功能。
2. **模型配置留白**：`config/models.json` 不预填任何具体模型/提供商。只提供**空模板结构**（base_url + api_key 环境变量名 + 模型名），由用户日后亲自填写。
3. **所有角色名称一律中文**：角色定义、UI 展示、prompt、日志中全部使用中文名（狼人、预言家、女巫、猎人、村民），不引入英文角色标识符。
4. **狼人夜晚攻击目标先做一轮内部协商**（详见 6.3）。
5. **断线/刷新/重连**：游戏**暂停**直到断线玩家重连；重连后恢复完整状态（详见 7.1）。
6. **发言顺序**：玩家编号 1→N 依次发言；AI 发言要求在 prompt 中输出结束标记，后端识别到后自动推进到下一人（详见 6.4）。
7. **房间创建极简**：房主只设「总玩家人数」，人类逐个加入，开始游戏时 AI 自动补满空位（详见 7.1）。
8. **角色分配全随机**。
9. **LLM 调用串行**：同一时刻只有一个玩家发言/行动，LLM 调用排队等待，流式输出（文本 + TTS 音频）逐段播送（详见 7.2）。
10. **玩家间调用隔离**：每个 AI 玩家拥有**独立对话会话**（独立消息历史、独立上下文），多个玩家共用同一模型时互不干扰（详见 7.2）。
11. **API Key 缺失处理**：启动时校验，缺失即打印明确警告并禁用对应模型（详见 7.4）。

## 3. 关键决策与调研依据

| 决策点 | 结论 | 依据 |
|---|---|---|
| 后端起点 | **从零写 FastAPI 项目**，参考 wolf_bot 的角色/裁判/prompt 设计 | 调研确认 wolf_bot 是「单局单实例 + HTTP 轮询 + PixiJS 前端」，无 WebSocket 无多房间，改造≈重写；但其游戏逻辑设计优秀值得借鉴 |
| LLM 接入 | **自写 OpenAI 兼容客户端**（HTTPS 直调 /chat/completions），不用 LiteLLM | LiteLLM 2026-03 发生供应链攻击（1.82.7/1.82.8 被植入后门）；且只需 2-3 个模型，自写客户端约 100 行，DeepSeek/Qwen/豆包/GLM/Kimi 均提供 OpenAI 兼容端点 |
| 前端 | **Alpine.js 3.x + 原生 WebSocket**，无构建步骤 | UI 仅房间/游戏/发言/投票，Alpine.js 7KB 免构建，代码量约为 Vue 方案一半 |
| TTS | **edge-tts**（免费、中文音色 20+、流式） | 调研验证可行；因发言串行，不存在多路音频冲突 |
| 广播 | `asyncio.gather(..., return_exceptions=True)` 并发广播 | 100+ 连接时朴素 for 循环广播会慢（实测数据） |
| 异地联机 | 局域网为主，Tailscale 作为后期可选里程碑 | Tailscale 国内延迟无数据且有性能降级记录，不阻塞主流程 |
| 并发目标 | 12 房间 × 9 玩家 WebSocket 完全可行 | FastAPI 单机实测 45k 并发连接 |

## 4. 技术栈


## 6. 游戏设计

### 6.1 角色定义（全部中文）

| 角色 | 阵营 | 数量(9人局) | 技能 |
|---|---|---|---|
| 狼人 | 狼人阵营 | 3 | 夜晚协商杀一人；互知同伙 |
| 预言家 | 好人阵营 | 1 | 夜晚查验一人身份 |
| 女巫 | 好人阵营 | 1 | 解药/毒药各一次 |
| 猎人 | 好人阵营 | 1 | 被放逐或被狼杀时可开枪带一人 |
| 村民 | 好人阵营 | 3 | 无技能 |

- 6 人局：村民×4 + 预言家×1 + 狼人×1
- 9 人局：如上表
- 12 人局：狼人×4 + 预言家×1 + 女巫×1 + 猎人×1 + 守卫×1 + 村民×4（守卫为 12 人局可选扩展，M2 阶段先做 9 人局，12 人局角色池可配置）
- 角色名是唯一标识符（`role == "狼人"`），全项目不出现英文角色名

### 6.2 流程

```
房主创建房间 → 人类加入 → 房主开始 → 随机分配角色（私密推送每人）
→ 夜晚：狼人协商杀一人 → 预言家查验 → 女巫救/毒 → 天亮公布死者
→ 白天：编号 1→N 依次发言 → 投票（综合推理）→ 放逐 + 猎人可能开枪
→ 循环至任一阵营胜利
```

### 6.3 狼人夜晚协商（用户指定：先内部对话一轮）

```
1. 按狼人编号顺序，每只狼人向同伙发表一句攻击目标建议（LLM 调用，串行）
2. 建议汇总后，每只狼人各自投票选目标（一轮）
3. 得票最多者为击杀目标；平票则随机
4. 协商过程仅狼人可见（其他玩家收到「狼人正在商议中…」）
```

### 6.4 发言顺序与推进（用户指定）

- 白天按玩家编号 **1→N 依次发言**，每人一轮，顺序固定
- AI 发言：`speaker.py` 调 LLM 流式生成，边生成边广播文本增量；prompt 要求以 `【发言结束】` 结尾，后端检测到该标记后广播 `speech_end`，自动推进到下一人
- 人类发言：前端输入框 + 「结束发言」按钮，点击后推进
- 全流程串行：同一时刻只有一人发言，LLM 调用排队

### 6.5 投票（保留说明书第 8 章设计）

- 全部发言结束后，进入投票阶段
- 每个 AI 玩家：发言记录**随机乱序** → 分步 CoT（Step1 矛盾点 / Step2 证据强度 / Step3 决策）→ 严格输出 `投票: <玩家编号>`，解析失败重试 1 次
- 人类玩家：前端投票面板点选
- 汇总：票数最高者放逐；平票则无人出局
- 人类与 AI 投票均串行收集，全部收齐后结算

### 6.6 胜负判定（确定性逻辑，不用 LLM）

- 狼人全部死亡 → 好人胜利
- 狼人数 ≥ 好人数 → 狼人胜利

## 7. 关键机制设计

### 7.1 房间与连接

**创建房间**：房主输入昵称 → 选总玩家人数（6/9/12，默认 9）→ 创建成功获得房间码。其余人类玩家输昵称 + 房间码加入。房主点击「开始游戏」时，系统**自动创建 AI 玩家补满空缺**（AI 玩家数 = 总人数 - 已加入人类数），AI 玩家自动获得昵称（如「AI-小狼」等中文名池）与随机分配模型（从配置的模型池中取）。

**断线暂停与重连**（用户指定）：
- 玩家标识 = 房间码 + 昵称（重连凭据）。同一昵称重复连接视为同一玩家
- 任一玩家 WebSocket 断开 → 广播「XX 已掉线，游戏暂停」→ **冻结当前阶段**（正在进行的 LLM 调用允许完成但不再启动新的）
- 断线玩家用相同昵称重新连接 → 服务端推送**完整状态快照**（角色、可见历史、当前阶段、自己的行动界面状态）→ 广播「XX 已回来，游戏继续」→ 恢复推进
- 刷新页面 = 断线 + 重连，同一机制

### 7.2 LLM 接入（自写 OpenAI 兼容客户端）

- `llm_client.py`：httpx 异步调用 `{base_url}/chat/completions`，支持流式（SSE 解析 `delta.content`），超时 60s，失败重试 1 次
- `llm_pool.py`：**玩家会话隔离**——为每个 AI 玩家持有独立 `messages[]` 历史（系统 prompt + 其可见的游戏事件 + 其发言记录）。同模型多玩家共用客户端实例但会话完全独立，互不可见、互不覆盖
- **串行调度**：全局一个异步队列 `asyncio.Queue`，所有 AI 行动（发言/投票/夜晚行动/狼人协商）按顺序入队执行，同一时刻只有一个 LLM 调用在跑
- 流式发言：`speaker.py` 边收 chunk 边广播 `{type:"speech_delta", ...}`，同时按句切分交给 `tts.py` 生成音频 chunk 广播 `{type:"speech_audio", ...}`

### 7.3 语音播报（edge-tts）

- 流式：`edge_tts.Communicate(text, voice)` 逐 chunk 广播（base64 mp3）
- 因发言串行，同一时刻只有一路音频，无多路冲突问题（简化说明书 9.3 的多路播放器）
- 前端：Web Audio API 解码播放；**iOS Safari autoplay 限制**——首次用户点击（加入房间按钮）时初始化 AudioContext 并 resume，之后所有播放不再受阻
- 音色：默认 `zh-CN-XiaoxiaoNeural`；用户日后在 models.json 给每个模型配可选 `tts_voice`，留白

### 7.4 配置与 API Key 检查

- `config/models.json` **留白模板**（用户日后自填，格式见下）
- `.env`：`OPENAI_API_KEY=...`、`DEEPSEEK_API_KEY=...` 等（由用户按自填模型确定）
- 启动时：解析 models.json 中每个模型 → 检查其 `api_key_env` 指定的环境变量是否存在 → 缺失则**打印醒目的中文警告**（`⚠️ 模型「XX」缺少 API Key（未设置环境变量 XXX），该模型已禁用`）→ 被禁用的模型不参与分配；全部模型缺失时仍可启动（纯人类局或仅测试 UI）

```json
// config/models.json — 留白模板，由用户亲自填写
{
  "models": [
    {
      "name": "示例模型A",            // 展示名，可中文
      "provider": "openai_compatible", // 固定值
      "base_url": "",                  // 例如 https://api.deepseek.com/v1
      "api_key_env": "DEEPSEEK_API_KEY",
      "model": "",                     // 例如 deepseek-chat
      "tts_voice": ""                  // 可选，留空用默认音色
    }
  ]
}
```

## 8. 实施里程碑（每阶段完成后必须验证通过再进入下一阶段）

### M0 — 项目骨架（约 1 小时）
- 初始化目录结构（第 5 节）、`requirements.txt`、`config/models.json` 留白模板、`.env.example`、启动脚本
- `main.py`：静态文件服务 + `/ws` 空路由 + 启动时打印局域网 URL + API Key 校验
- `index.html` + `app.js`：Alpine.js 骨架，房间创建/加入表单
- **验收**：`python -m backend.main` 启动无报错；浏览器打开 `http://127.0.0.1:8000` 看到房间表单；缺失 Key 时终端打印中文警告

### M1 — 房间与连接（约 1 小时）
- `room/manager.py`：创建/加入/离开房间，房间码，人数管理，AI 补位
- `ws_handler.py`：消息路由、心跳、**断线检测 → 广播暂停**、**重连 → 状态快照恢复**
- **验收**：两个浏览器标签页加入同一房间，互相可见；关掉一个标签页，另一侧收到「XX 已掉线，游戏暂停」；重连后恢复

### M2 — 游戏核心（纯 AI 可玩）（约 3-4 小时）
- `roles.py`（全中文）、`state_machine.py`、`judge.py`（杀/救/毒/验/开枪/胜负）
- 夜晚：狼人协商（6.3）→ 预言家 → 女巫；天亮公布
- 白天：编号顺序发言推进框架；投票结算；猎人开枪
- 人类玩家在 M2 先以「占位 AI」替代（后端先不接真实 LLM，用**假 AI 输出固定话术**跑流程），保证游戏规则逻辑正确
- **验收**：脚本驱动一局完整 9 人局，流程走通（发言→投票→出局→胜负），`logs/replay_*.json` 记录完整

### M3 — LLM 接入（约 3 小时）
- `llm_client.py`（OpenAI 兼容 + 流式）、`llm_pool.py`（会话隔离 + 串行队列）
- `prompts.py`：角色信息隔离 prompt（第 6.3 节说明书的模板），发言含 `【发言结束】` 标记
- `speaker.py`：流式发言驱动 + 结束标记推进
- `voting.py`：乱序 + 分步 CoT + 结构化解析
- **验收**：配置 2 个模型（用户提供 Key 或用 mock），9 人纯 AI 局中 AI 能按顺序发言（文本流式出现）、发言以标记结束自动推进、投票输出推理后正确结算；两个 AI 用不同模型时各自发言正常且互不串话

### M4 — 人类玩家交互（约 2 小时）
- 前端：自己的角色卡（中文角色名）、夜晚行动界面（预言家输入编号查验 / 女巫选择救/毒 / 狼人看到同伙）、发言输入框 + 「结束发言」、投票面板
- 后端：人类行动消息路由（`human_action`），等待人类输入时不推进（不超时）
- **验收**：1 人类 + 8 AI 混合局完整玩完一局，人类能查验/救毒/发言/投票，AI 对人类的发言做出反应

### M5 — 语音播报（约 1-2 小时）
- `tts.py` edge-tts 流式封装；`speaker.py` 集成音频 chunk 广播；前端 Web Audio 播放 + iOS 手势初始化
- **验收**：AI 发言时同步出声（第一个音频包 < 1.5s）；连续发言不互相覆盖；iPhone Safari 上能听到声音

### M6 — 部署与联机（约 1 小时）
- 启动横幅打印全部可访问 URL（局域网 IP:8000）；README.md（安装、配置模型、启动、局域网加入、异地联机说明）
- 异地联机（Tailscale）作为**可选后续**：README 中给出步骤，不阻塞交付
- **验收**：手机连同一 WiFi 打开 `http://<主机IP>:8000` 加入游戏玩一局；朋友按 README 能在局域网玩通

## 9. 端到端验证（最终验收）

1. **三局全流程**：好人胜 / 狼人胜 各完整跑 1 局（9 人：AI 参与），验证胜负判定、猎人开枪、女巫毒药等分支
2. **混合局**：1 人类 + 8 AI 玩完一局，人类能完成所有角色行动（至少当一次预言家、一次村民）
3. **断线恢复**：游戏中关掉一个浏览器 → 游戏暂停 → 重连后从断点继续
4. **多人局域网**：两台设备（电脑 + 手机）加入同一房间玩一局
5. **语音**：至少 1 个 AI 角色发言有声音
6. **多模型**：2 个不同模型分别扮演不同 AI 玩家，无串话、无会话污染

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| LLM 输出不按格式（结束标记/投票格式） | 解析失败重试 1 次，仍失败则用默认值（该玩家投弃权/发言以截断文本结束） |
| edge-tts 偶发网络失败 | 静默降级：跳过该句音频，只播文本（游戏不中断） |
| 模型 API Key 无效/欠费 | 启动校验 + 首次调用失败时房间内广播明确中文错误提示 |
| 断线玩家长时间不回来 | 游戏无限暂停（用户明确要求暂停制）；房主可手动「踢出该玩家」并继续（M4 后补充，先不做） |
| 局域网 IP 变化 | 启动横幅打印当前 IP；README 说明用 `ipconfig`/`ifconfig` 查询 |
